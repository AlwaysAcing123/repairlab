# First original-model baseline — October 29, 2026

**8/24 proposed repairs passed (33.3%).** These are custom development tasks, one
response per task, without execution feedback. No model weights were updated and
this is not a final held-out generalization result.

The private [Kaggle notebook](https://www.kaggle.com/code/alwaysacing/repairlab-original-model-baseline)
ran successfully as version 1. Kaggle confirmed COMPLETE. Only public task information
was uploaded. Model responses remained text in the GPU notebook, were downloaded,
then executed and independently graded in restricted local containers.

## Frozen configuration

- Model: `Qwen/Qwen3-0.6B`, revision `c1899de289a04d12100db370d81485cdf75e47ca`.
- Original weights, no adapter, no training, seed 7, greedy decoding, thinking disabled.
- One response per task, maximum 1,024 generated tokens and 3,072 input tokens.
- Same 24 admitted development tasks; none added, removed, or changed after generation.
- Public specification, buggy function, and examples in the prompt; independent
  expected outputs and reference repairs excluded from both model input and GPU files.
- Complete-source responses; strip outer whitespace and at most one enclosing code
  fence. No semantic repair, retries, or selection among multiple answers by the harness.
- Kaggle Tesla T4, recorded dtype `torch.bfloat16`, Transformers 5.2.0. Full package
  versions, GPU information, and prompt configuration are preserved in the output.

The executor and grader use the source fingerprint frozen in `submission-plan.json`,
matching the earlier validated package. Before submission, the notebook generator
was updated to expose one GPU, record its input budget/extraction rule, and sanitize
external benchmark IDs for raw-response filenames. A formatter test verifies that
actual newlines survive source extraction. **24/24 automated tests passed**, including
nine real Docker integration tests. The revised custom notebook was actually executed;
the external HumanEvalFix notebook still has only structural validation.

## Results

| Task category | Passed / evaluated |
| --- | --- |
| Validation helpers | 1/8 |
| Collection processing | 3/8 |
| Control-flow helpers | 4/8 |
| Total | **8/24** |

All 24 generations completed without generation errors or missing responses. Of the
16 failed repairs, 13 repeated the buggy source unchanged, two changed the program
without correcting it, and one returned JSON test data instead of a Python function.
That invalid response remains a failure in the 24-task denominator.

For example, `quantity-range` kept `1 <= quantity < maximum` despite a specification
requiring an inclusive upper boundary. `bounded-queue` added a condition for nonnegative
capacity, but still returned the entire list for capacity zero. Successful repairs
included `page-slice`, `drop-missing`, `running-totals`, `retry-decision`, `capped-backoff`,
`cache-expiry`, `remaining-budget`, and `required-fields`.

Success requires all public and private checks, including type preservation and no
input mutation. The grade is limited to the declared finite input domains. The 24
fixtures share algorithmic patterns and are not 24 independent bug families.

## Interpretation and next experiment

The original model sometimes succeeds and sometimes fails, making this a useful
feasibility result. Frequent unchanged submissions suggest a weakness worth diagnosing
before training. This run alone cannot tell us whether the cause is task understanding,
prompt format, insufficient debugging behavior, or model capacity.

The next experiment should connect the same model to the bounded interactive tool
loop and compare its behavior with this single-response reference. Execution feedback
may help; that is not yet measured. Interactive comparisons must record their extra
token and tool budgets. Subsequent original-versus-trained comparisons must use the
same interactive protocol. Do not attribute interaction or prompt changes to learning.

Use these development findings to design independent training programs and a new
frozen evaluation set. No supervised fine-tuning, RL, or HumanEvalFix model evaluation
has yet been performed in RepairLab.
