# Second sealed final test — November 5, 2026

The first final test was opened once on November 5 and can no longer serve as an unseen
test. This is its replacement, built for the next comparison, which uses Qwen3-1.7B.
Nothing here is a model score. **Update, November 6:** this test was opened once, as
planned, and is now spent. See [the 1.7B results](scaleup-results-20261106.md).

## Why 48 tasks

With 24 tasks, a 2-task difference is noise. The recovery and RL adapters differed by
exactly that on both earlier splits, so neither result could be called reliable. Twice
as many tasks gives a real difference of the same size twice as many tasks on which to
show itself. Fewer than 6 tasks won by only one side can never reach p < 0.05 in a
sign test, whatever their direction.

## Contents

`repairlab/final2/programs.py` holds 48 new single-function repair tasks, in their own
package so earlier fingerprints stay meaningful.

| Family | Tasks | Bug categories |
| --- | ---: | --- |
| Validation | 16 | 4 each of missing condition, comparison, off by one, update logic |
| Collections | 16 | 4 each |
| Control flow | 16 | 4 each |

They have 144 public examples and 17,997 private checks. In the Docker grader, all
**192 authored controls matched**: on every task the bug fails, the reference and a
different correct version pass, and a copy that hard-codes the public answers fails.

On `safe-average`, `season-of-month`, and `life-cell`, only a public example exposes
the bug, as on `letter-grade` before. Success still requires every public and private
check to pass.

## Separation

`final2_leakage_report()` compared each new task with all 120 earlier programs:
development, both training sets, the opened final test, and the warm-up programs. That
is 5,760 pairs, with **no hard failures**.

Review caught two real problems, and both drafts were replaced:

- `never-overdrawn` used the same running-balance algorithm as training program
  `balanced-parens`, which recovery training nearly memorized. It became
  `luhn-checksum`.
- `column-sums` nearly copied the code and wording of opened final-test task
  `transpose-rows`, which a later model may train on. It became `move-zeros-to-end`.

The remaining 18 near pairs were read and pinned in `REVIEWED_FINAL2_NEAR_PAIRS`.
Eight are string or list checks that agree only because both return False on at least
94% of shared inputs. The other ten share a one-line skeleton, such as
`all(... for x in xs)` or `range(a, b + 1)`, while computing different functions with
different fixes. A new near pair fails the tests until someone reviews it.

## Sealing

- `reject_final2()` refuses these tasks by content, not just ID, in any model-facing
  path. Every earlier program set passes it.
- No existing script references the package, and a test pins that.
- The manifest records zero model evaluations. Manifest SHA-256:
  `397adde99b735a6d202a7c6fc0b76eb23b944e5f209f376724cf21233557adbc`.

Like every earlier task, these are AI-authored and not independently human-reviewed.

## One fix to shared code

The leakage check's 20 ms per-call timer could fire in the instant before its guarded
block began. Under load that crashed the check instead of counting a timeout. The timer
is now armed inside the block in `repairlab/curriculum/splits.py`. The curriculum
fingerprint therefore changed from `1661384f…` to `8c795d54…`. No verifier compares it
with current code, and every earlier run keeps a source snapshot of the code it ran.
